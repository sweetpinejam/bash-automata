# Tactical Field Manual: The Phantom Signal (POSIX Signals, Kernel Dispositions & Hot Reloads)

## 1. Systems Mental Model: The Linux Kernel Signal Architecture
Signals are standardized software interrupts generated by the Linux kernel or other processes. When the kernel delivers a signal to a process:
1. The kernel checks the process's **Signal Disposition Table** (stored in the process's `sighand_struct`).
2. If the signal is **ignored**, execution continues uninterrupted.
3. If the signal is **trapped** with a custom handler, the kernel saves the current execution context, switches the stack to execute the trap handler routine, and then resumes normal execution.
4. If the signal is **untrapped**, the kernel executes the **Default Action**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   DEFAULT KERNEL SIGNAL DISPOSITIONS                   │
│                                                                        │
│   Signal      Num   Production Purpose           Default Linux Action  │
│  ─────────   ─────  ──────────────────────────   ────────────────────  │
│   SIGHUP       1    Hot Configuration Reload     TERMINATE PROCESS 💥  │
│   SIGINT       2    Terminal Interrupt (Ctrl+C)  TERMINATE PROCESS 💥  │
│   SIGUSR1     10    On-Demand Telemetry Dump     TERMINATE PROCESS 💥  │
│   SIGUSR2     12    Log Reopening (Logrotate)    TERMINATE PROCESS 💥  │
│   SIGTERM     15    Graceful Drain & Shutdown    TERMINATE PROCESS 💥  │
│   SIGKILL      9    Emergency Forced Kill        TERMINATE (Cannot Trap)
└────────────────────────────────────────────────────────────────────────┘
```

> [!CAUTION]
> **The Untrapped Crash Catastrophe**:
> Notice the default action for unhandled `SIGHUP` and `SIGUSR1`: **Terminating the process!**
> When orchestrators (Kubernetes, Systemd, CI/CD runners) send `kill -HUP $PID` expecting a zero-downtime configuration reload, an untrapped daemon does not reload—**it crashes immediately with exit code 129 (`128 + 1`)**, taking down active connections and causing widespread service outages!

## 2. Zero-Downtime Hot Reloading Architecture

In enterprise infrastructure (NGINX, Envoy, Prometheus, HAProxy), daemons must never drop active client connections just because an administrative setting changed.

Instead of restarting the binary:
1. Configuration files (`app.conf`) are rewritten on disk.
2. The orchestrator emits `kill -HUP $PID`.
3. The daemon's trapped handler re-parses `app.conf` in memory.
4. Active TCP connections and client transactions proceed without interruption.

```
       [ Orchestrator ]
              │
              ├── 1. Writes new backend config to app.conf
              │
              └── 2. Sends SIGHUP (kill -HUP $PID)
                            │
                            ▼
                  [ Linux Kernel VFS ]
                            │
                  (Trapped by proxy.sh)
                            │
                            ▼
              ┌───────────────────────────┐
              │      reload_config()      │
              │  - source app.conf        │
              │  - Updates $BACKEND       │
              │  - Logs CONFIG_RELOADED   │
              └─────────────┬─────────────┘
                            │
                            ▼
           [ Active Loop Continues Running ]
```

## 3. The Responsive Event Loop: Avoiding the `sleep` Trap

A common bug in Bash daemon development:
```bash
# 💥 SLOW SIGNAL DELIVERY BUG:
while true; do
    sleep 30   # <-- Signal delivery is delayed until the 30s sleep completes!
done
```
When a simple command like `sleep 30` runs in the foreground, Bash waits for the command to finish before executing pending signal handlers.

### The Production Pattern: Background Sleep + `wait`:
```bash
while $running; do
    (( requests_handled += 1 ))

    # Sleep in the background, then wait on its PID:
    sleep 0.1 &
    wait $! 2>/dev/null || true
done
```
* The POSIX `wait` built-in returns **immediately** with an exit status greater than 128 whenever an unmasked or trapped signal arrives!
* The trap handler fires instantaneously within milliseconds of receiving `kill -HUP` or `kill -USR1`.

## 4. Syntax & Trapping Mechanics in Bash

```bash
# Define handler functions
reload_config() {
    source "$CONF_FILE"
    echo "CONFIG_RELOADED: BACKEND=$BACKEND" >> "$LOG_FILE"
}

dump_metrics() {
    echo "REQUESTS_HANDLED=$requests_handled BACKEND=$BACKEND" > "$METRICS_FILE"
}

terminate_daemon() {
    running=false
}

# Bind handlers to signals
trap reload_config HUP
trap dump_metrics USR1
trap terminate_daemon TERM INT EXIT
```

## 5. Real-World Gotchas & Pitfalls

1. **Unlinking the PID File**:
   Always record the daemon's process ID (`echo "$$" > proxy.pid`) on startup, and ensure your `EXIT` trap unlinks it to prevent stale PID references.
2. **Signal Re-entrancy**:
   If `SIGHUP` arrives while the daemon is inside `reload_config()`, modern Linux shells queue subsequent signals until the active trap returns. Keep trap handlers concise and fast.
3. **Resetting Signals to Default**:
   To reset a signal back to its default kernel behavior: `trap - HUP`.
   To completely ignore a signal so it is silently discarded: `trap '' HUP`.

* **`man 7 signal`**: Comprehensive Linux manual on signal names, numerical identifiers, default dispositions, and real-time signal behaviors.
* **`man 2 sigaction`**: Low-level system call interface detailing `SA_RESTART`, signal blocking masks, and kernel signal context switches.

## 7. Self-Assessment Checklist
Before modifying `proxy.sh`:

1. **What is the default kernel action if an unhandled `SIGHUP` or `SIGUSR1` is sent to a process?**
   * *Answer*: Immediate process termination.
2. **Why does running `sleep 60` in the foreground delay signal trap execution?**
   * *Answer*: Foreground simple commands block the shell; Bash defers running trapped handlers until the foreground command completes.
3. **How does `sleep 0.1 & wait $!` achieve millisecond signal responsiveness?**
   * *Answer*: The `wait` built-in immediately unblocks upon receiving any trapped signal, executing the handler without waiting for the sleep process.
4. **How do you instruct Bash to completely ignore a signal?**
   * *Answer*: By binding an empty string: `trap '' SIGNAL`.
5. **Why should a daemon write its PID to a file like `proxy.pid` at startup?**
   * *Answer*: To provide an unambiguous, deterministic target PID for monitoring scrapers and orchestrator reload signals (`kill -HUP $(cat proxy.pid)`).
